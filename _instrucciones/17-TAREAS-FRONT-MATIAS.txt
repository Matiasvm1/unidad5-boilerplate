### Qué problema resuelve

El boilerplate de la cátedra trae las pantallas dibujadas con datos de ejemplo, pero la base
sobre la que se apoyan no sirve tal como está (especificación, sección 0.3):

- **No se conecta con el backend (B8).** `.env.development` apunta al puerto `5142` y el backend
  corre en el `5278`. Además `vite.config.js` arma un proxy para `/api` que nunca se usa, porque
  Axios llama a la URL completa.
- **El router se crea en cada render (B9).** `createBrowserRouter(routes)` está adentro de la
  función `App`: cada vez que React redibuja `App`, arma un router nuevo.
- **Rutas duplicadas (B10).** `/admin/patients` y `/admin/patient-search` muestran la misma
  página, y `/admin/appointments` solo redirige a `/admin/patients`.
- **Archivos sin uso (B11).** `LoginPage.jsx` y `LoginForm.jsx` no están en ninguna ruta, y
  `login.js` llama a un tercer login (`api/auth/login`) que el backend no tiene.
- **Los errores llegan crudos.** Cuando un pedido falla, la página recibe el error de Axios y
  tiene que bucear en `error.response.data`. Cada pantalla lo hacía distinto (y buscaba códigos
  numéricos como `1000` que el backend no usa).
- **Solo hay cuatro componentes compartidos** (`Button`, `Input`, `Card`, `TablePagination`),
  sueltos en `shared/components/`. Las páginas copiaban íconos SVG enteros, tablas y buscadores
  adentro de cada archivo (B13).
- **Los archivos se guardan con fin de línea de Windows.** Git para Windows convierte los saltos
  de línea a CRLF al bajar los archivos, y Prettier (que corre adentro de `npm run lint`) los
  rechaza.

### Por qué así

- **Todo lo compartido entra en esta tarea, aunque todavía no lo use nadie.** Las tareas 3 a 9
  se hacen en paralelo, cada una en su carpeta de `src/modules`. Si cada uno tuviera que crear
  el `DataTable` o el `ConfirmDialog` que necesita, habría tres versiones distintas o tres
  personas tocando el mismo archivo de `shared/` a la vez. Por eso la base trae **todo** el kit:
  átomos, moléculas, el `DataTable`, los hooks genéricos y también los de catálogo
  (`useDoctors`, `useDoctorOptions`, `useDoctorsBySpecialty`, `useSpecialtyOptions` y
  `catalogService`). **Es esperado que al terminar la tarea 1 casi todos estos archivos no los
  importe ninguna página**: las páginas siguen siendo las del boilerplate. Cada uno se empieza a
  usar en la tarea que lo necesita (la tabla de "Qué afecta" dice cuál).
- **Las páginas del boilerplate no se reescriben acá.** Solo se les corrigen los `import` para
  que sigan funcionando después de mover los componentes (y, en `AppointmentsPage`, el nombre de
  una variante de `Button` que cambió). Siguen mostrando sus datos de ejemplo
  hasta que la tarea de cada pantalla las reescriba. Así esta tarea se puede revisar sola: si
  algo se ve distinto después de la 1, es un error.
- **Los componentes del boilerplate se mueven, no se duplican** (especificación, secciones 3.4 y
  10): `Button` y `Card` pasan a `atoms/`, `Input` a `atoms/` (sin la etiqueta ni el error, que
  ahora son de `FormField`) y `TablePagination` a `molecules/`. Se les agregan las props que
  faltaban en vez de crear un segundo componente que haga lo mismo.
- **Un solo formato de error: `ApiError`** (especificación, 6.3). El interceptor de Axios
  convierte cualquier falla en un objeto con `status`, `errorCode`, `message` y `details`. Las
  pantallas nunca ven un error de Axios (17-PLAN-FRONT, sección 8.7).
- **CORS directo, sin proxy** (especificación, 4.3). El proxy de Vite solo existe en el servidor
  de desarrollo: el build de producción igual necesitaría CORS. Se quita para no dejar
  configuración muerta, y se fija el puerto `5173`, el único que el backend acepta.
- **`.gitattributes` con LF** para que el formato de los archivos no dependa de la
  configuración de Git de cada uno.
- **El 401 global y la sesión no se tocan.** Son de la tarea 2 (Nicolás). En `axiosInstance.js`
  solo cambian dos líneas; el resto sigue siendo del boilerplate.

#### Grupo A — Configuración

##### Archivo 1 de 59 · `.gitattributes`

| **Qué hacer** | **Crear** el archivo nuevo y escribir este código (4 líneas) |
|---|---|
| **Carpeta** | la raíz del proyecto (donde está `package.json`) |
| **Archivo** | `.gitattributes` |
| **Ruta completa** | `.gitattributes` |

````
* text=auto eol=lf
*.svg text eol=lf
*.png binary
*.ico binary
````

**Qué hace y por qué:**

Le dice a Git cómo tratar cada tipo de archivo. No es código de la app.

- `* text=auto eol=lf`: todo archivo que Git reconozca como texto se guarda y se baja con fin de
  línea LF (el de Linux y Mac), sin importar el sistema operativo.
- `*.svg text eol=lf`: los SVG son texto (son XML), así que también van con LF.
- `*.png binary` y `*.ico binary`: las imágenes nunca se convierten. Si Git les cambiara bytes
  "de fin de línea", las rompería.

**Por qué hace falta:** Git para Windows viene configurado con `core.autocrlf=true`, que al bajar
los archivos les pone CRLF (el fin de línea de Windows). Prettier exige LF, y como el ESLint del
boilerplate corre Prettier como una regla más, `npm run lint` falla en todos los archivos con
errores **"Delete `␍`"** (el `␍` es el CR que sobra).

**Paso obligatorio, apenas creás este archivo y antes de escribir cualquier otro.** El
`.gitattributes` solo se aplica a los archivos que Git escribe **de ahora en adelante**. Los que
ya bajaste con el `git clone` siguen con CRLF en tu disco, y el lint sigue fallando. Hay que
hacer que Git los vuelva a escribir:

```bash
git add .gitattributes
git commit -m "wip: force LF"   # commit intermedio: se junta con el resto al final (17-PLAN-FRONT, sección 5)
git rm --cached -r . -q         # saca todos los archivos del índice de Git (NO los borra del disco)
git reset --hard                # vuelve a escribir todos los archivos desde el commit, ahora con LF
git status                      # tiene que decir "nothing to commit, working tree clean"
```

- `git rm --cached -r .` le hace creer a Git que los archivos no están en el índice, y
  `git reset --hard` los vuelve a sacar del último commit. Al escribirlos de nuevo, Git aplica el
  `.gitattributes` y quedan con LF.
- **`git reset --hard` descarta cualquier cambio sin commitear.** Por eso se hace ahora, cuando
  lo único que hiciste es el `.gitattributes` y ya está commiteado. Nunca lo corras con trabajo a
  medio hacer.
- Si más adelante un archivo suelto sigue con CRLF (por ejemplo, uno que copiaste de otro lado),
  alcanza con borrarlo y pedírselo de nuevo a Git: `git checkout -- <archivo>`.

````js
  static fromAxiosError(error) {
    const { response } = error;

    if (!response) {
      return new ApiError({
        status: 0,
        errorCode: NETWORK_ERROR,
        message: 'No se pudo conectar con el servidor',
      });
    }

    const { status } = response;
    const body = response.data ?? {};

    return new ApiError({
      status,
      errorCode: body.errorCode ?? 'UNKNOWN_ERROR',
      message: ownMessages[status] ?? body.message ?? UNEXPECTED_MESSAGE,
      details: Array.isArray(body.details) ? body.details : [],
    });
  }
}

export { ApiError, NETWORK_ERROR };
````

**Qué hace y por qué:**

La forma única de los errores (17-PLAN-FRONT, sección 8.7; especificación 6.3 y 6.4). Es una
**clase** que extiende `Error`, así sigue siendo un error de JavaScript de verdad (se puede
lanzar con `throw` y atrapar con `catch`), pero con cuatro campos propios:

- El `constructor` recibe `{ status, errorCode, message, details }`. `super(message)` le pasa el
  mensaje a `Error`, y `details = []` hace que, si no viene, sea una lista vacía.
- `static fromAxiosError(error)` es el traductor. `static` quiere decir que se llama sobre la
  clase (`ApiError.fromAxiosError(...)`), sin crear un objeto antes.
  - **Sin `response`** (backend apagado, sin red, CORS bloqueado): `status: 0`,
    `errorCode: 'NETWORK_ERROR'` y el mensaje "No se pudo conectar con el servidor".
  - **Con `response`**: toma el `errorCode` y el `message` del cuerpo que manda el backend.
- `ownMessages` son los únicos textos propios del front: para `429` y `500` (especificación
  6.4). Todo lo demás muestra el `message` del backend, que ya viene en español.
- `??` es el operador "si lo de la izquierda es `null` o `undefined`, usá lo de la derecha". Así
  `ownMessages[status] ?? body.message ?? UNEXPECTED_MESSAGE` quiere decir: el texto propio si lo
  hay; si no, el del backend; si tampoco, el genérico.
- `Array.isArray(body.details)` se asegura de que `details` siempre sea una lista, para que nadie
  tenga que preguntar antes de recorrerla.

Lo importa `axiosInstance.js`. Exporta también `NETWORK_ERROR` por si una pantalla necesita
distinguir "no hay conexión".

````js
// parts (never toISOString, which shifts to UTC and can change the day).
// Spec 7.2: this is the only place where dates are converted.

const WEEK_LENGTH = 7;

function toIsoDate(date) {
  const year = date.getFullYear();
  const month = String(date.getMonth() + 1).padStart(2, '0');
  const day = String(date.getDate()).padStart(2, '0');

  return `${year}-${month}-${day}`;
}

// "2026-08-10" -> local Date at midnight.
function fromIsoDate(iso) {
  const [year, month, day] = iso.split('-').map(Number);

  return new Date(year, month - 1, day);
}

function addDays(iso, amount) {
  const date = fromIsoDate(iso);

  date.setDate(date.getDate() + amount);

  return toIsoDate(date);
}

function todayIso() {
  return toIsoDate(new Date());
}

const longFormatter = new Intl.DateTimeFormat('es-AR', {
  weekday: 'long',
  day: 'numeric',
  month: 'long',
});
const shortMonthFormatter = new Intl.DateTimeFormat('es-AR', {
  month: 'short',
});

  return text.charAt(0).toUpperCase() + text.slice(1);
}

// The 7 days of the visible window, starting at `from`.
function buildWeek(from) {
  return Array.from({ length: WEEK_LENGTH }, (_, offset) => {
    const iso = addDays(from, offset);
    const date = fromIsoDate(iso);

    return {
      iso,
      weekday: capitalize(weekdayFormatter.format(date).replace('.', '')),
      dayNumber: date.getDate(),
      longLabel: formatLongDate(iso),
    };
  });
}

function formatLongDate(iso) {
  return capitalize(longFormatter.format(fromIsoDate(iso)).replace(',', ''));
}

// "2026-10-24" -> "24 oct 2026"
function formatShortDate(iso) {
  const date = fromIsoDate(iso);
  const month = shortMonthFormatter.format(date).replace('.', '');

  return `${date.getDate()} ${month} ${date.getFullYear()}`;
}

  const [date = '', time = ''] = (value ?? '').split(' ');

  return { date, time };
}

// True when the local date and time "YYYY-MM-DD HH:mm" is already behind `now`.
function isPastDateTime(value, now = new Date()) {
  const { date, time } = splitDateTime(value);

  if (!date || !time) {
    return false;
  }

  const moment = fromIsoDate(date);
  const [hours, minutes] = time.split(':').map(Number);

  moment.setHours(hours, minutes, 0, 0);

  return moment.getTime() <= now.getTime();
}

  toIsoDate,
````

**Qué hace y por qué:**

Todas las conversiones de fechas en un solo lugar (especificación 7.1 y 7.2). Hoy no la usa
nadie: la usan las tareas 6, 7, 8 y 9.

**El problema que resuelve:** `new Date("2026-08-10")` se interpreta como medianoche en UTC, y en
Argentina (UTC-3) eso es el **9** de agosto a las 21. Y `toISOString()` devuelve la fecha en UTC,
así que de noche puede dar el día siguiente. Por eso:

- `toIsoDate(date)` arma `"YYYY-MM-DD"` con `getFullYear()`, `getMonth() + 1` (los meses van de
  0 a 11) y `getDate()`. `padStart(2, '0')` completa con un cero a la izquierda: `8` → `"08"`.
- `fromIsoDate(iso)` separa el string con `split('-')`, convierte cada parte a número con
  `map(Number)` y arma la fecha **local** con `new Date(año, mes - 1, día)`.
- `addDays` y `todayIso` se apoyan en esas dos.
- Los `Intl.DateTimeFormat('es-AR', ...)` son los formateadores del navegador en español. Se
  crean **una vez**, afuera de las funciones, porque crearlos es caro y siempre son iguales.
- `buildWeek(from)` arma los 7 días de una semana. `Array.from({ length: 7 }, (_, offset) => ...)`
  crea una lista de 7 elementos llamando a la función con la posición (`offset` de 0 a 6); el
  `_` es el primer parámetro, que no se usa.
- `formatLongDate` da "Lunes 10 de agosto": le saca la coma que pone el navegador
  (especificación 7.1) y pone la primera letra en mayúscula con `capitalize`.
- `formatShortDate` da "24 oct 2026" (le saca el punto a "oct.").
- `splitDateTime("2026-08-10 09:00")` separa fecha y hora. `const [date = '', time = ''] = ...`
  pone `''` si falta alguna parte, y `(value ?? '')` evita que falle si `value` es `null`.
- `isPastDateTime` dice si un turno ya empezó: arma la fecha local con la hora y la compara con
  `now` usando `getTime()` (milisegundos).

````js
import { useEffect, useState } from 'react';

// Returns `value` once it has stopped changing for `delay` ms.
function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay);

    return () => clearTimeout(timer);
  }, [value, delay]);

  return debounced;
}

export default useDebounce;
````

**Qué hace y por qué:**

Devuelve el valor que le pasás, pero **recién cuando dejó de cambiar** durante `delay`
milisegundos. Lo usa el buscador para no mandar un pedido por cada letra (especificación 6.6 y
7.4).

- Cada vez que cambia `value`, el efecto arranca un temporizador con `setTimeout` que, al
  terminar, guarda el valor.
- La función de limpieza (`return () => clearTimeout(timer)`) cancela el temporizador anterior.
  Si escribís otra letra antes de los 400 ms, el temporizador viejo se cancela y arranca uno
  nuevo: solo el último llega a guardar el valor.

````js
import { useCallback, useState } from 'react';

// loading, error and run for one mutation (spec 10). `run` calls the service
// function, keeps `loading` true meanwhile and stores the ApiError when it
// fails. It rethrows, so the page can still branch on `errorCode`.
function useAsync(fn) {
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  const run = useCallback(
    async (...args) => {
      setLoading(true);
      setError(null);

      try {
        return await fn(...args);
      } catch (apiError) {
        setError(apiError);
        throw apiError;
      } finally {
        setLoading(false);
      }
    },
    [fn]
  );

  const reset = useCallback(() => setError(null), []);

  return { run, loading, error, reset };
}

export default useAsync;
````

**Qué hace y por qué:**

Para las **mutaciones** (crear, editar, borrar; especificación 10): guarda `loading` y `error` de
una sola llamada.

- `run(...args)` llama a la función del service con los mismos argumentos. Antes pone
  `loading` en `true` y borra el error anterior.
- `try` / `catch` / `finally`: si sale bien devuelve el resultado; si falla guarda el `ApiError`
  en `error` **y lo vuelve a lanzar** (`throw apiError`), para que la página pueda decidir qué
  hacer según el `errorCode`; y en los dos casos (`finally`) apaga `loading`.
- `reset` borra el error, por ejemplo al abrir de nuevo un diálogo.

````jsx
import { useEffect, useState } from 'react';
import Input from '../atoms/Input';
import useDebounce from '../../hooks/useDebounce';

// Search box with debounce. Calls onSearch with the trimmed text only when it
// has at least `minLength` characters, or with '' when it is shorter
// (spec 7.4: the API rejects names under 3 characters).
function SearchInput({
  id,
  label,
  placeholder,
  onSearch,
  minLength = 3,
  delay = 400,
  className = '',
}) {
  const [text, setText] = useState('');
  const debounced = useDebounce(text.trim(), delay);
  const term = debounced.length >= minLength ? debounced : '';

  useEffect(() => {
    onSearch(term);
  }, [term, onSearch]);

  return (
    <div className={className}>
      <label htmlFor={id} className="sr-only">
        {label}
      </label>
      <Input
        id={id}
        type="search"
        icon="search"
        placeholder={placeholder}
        value={text}
        onChange={(event) => setText(event.target.value)}
      />
    </div>
  );
}

export default SearchInput;
````

**Qué hace y por qué:**

El buscador con las reglas de la especificación 7.4: espera 400 ms sin escribir (`useDebounce`),
manda el texto sin espacios de los costados, y solo si tiene **3 o más** letras; con menos manda
`''`, que quiere decir "sin filtro" (el backend rechaza nombres de menos de 3).

- `text` es lo que se ve en el campo, y cambia con cada letra.
- `term` se calcula en cada dibujo a partir del valor ya demorado.
- El efecto llama a `onSearch(term)` **solo cuando cambia `term`**. Por eso escribir "ca" y
  después "c" no manda nada: `term` sigue siendo `''`.
- **Ojo para quien lo use:** `onSearch` está en las dependencias del efecto, así que la página
  tiene que pasarle una función estable, hecha con `useCallback`. Si no, el efecto correría en
  cada dibujo (en las tareas 3 y 4 se ve por qué importa).
- La `<label>` lleva `sr-only`: no se ve, pero el lector de pantalla la lee. El campo es
  `type="search"`.

````jsx
import { useEffect, useRef } from 'react';
import Button from '../atoms/Button';
import Alert from './Alert';

// Every destructive action goes through this dialog.
function ConfirmDialog({
  open,
  title,
  message,
  confirmLabel = 'Eliminar',
  cancelLabel = 'Cancelar',
  loading = false,
  error = '',
  onConfirm,
  onCancel,
}) {
  const cancelRef = useRef(null);

  useEffect(() => {
    if (!open) {
      return undefined;
    }

    cancelRef.current?.focus();

    const onKeyDown = (event) => {
      if (event.key === 'Escape' && !loading) {
        onCancel();
      }
    };

    document.addEventListener('keydown', onKeyDown);

    return () => document.removeEventListener('keydown', onKeyDown);
  }, [open, loading, onCancel]);

  if (!open) {
    return null;
  }

  return (
    <div className="fixed inset-0 z-50 flex items-center justify-center bg-black/40 px-4">
      <div
        role="alertdialog"
        aria-modal="true"
        aria-labelledby="confirm-dialog-title"
        aria-describedby="confirm-dialog-message"
        className="w-full max-w-sm bg-white rounded-xl shadow-xl p-6 flex flex-col gap-4"
      >
        <h2
          id="confirm-dialog-title"
          className="text-base font-bold text-med-text-main"
        >
          {title}
        </h2>
        <p id="confirm-dialog-message" className="text-sm text-med-text-sub">
          {message}
        </p>
        {error && <Alert tone="error">{error}</Alert>}
        <div className="flex flex-col-reverse sm:flex-row sm:justify-end gap-2">
          <Button
            ref={cancelRef}
            variant="secondary"
            onClick={onCancel}
            disabled={loading}
            className="min-h-11"
          >
            {cancelLabel}
          </Button>
          <Button
            variant="danger"
            onClick={onConfirm}
            loading={loading}
            className="min-h-11"
          >
            {confirmLabel}
          </Button>
        </div>
      </div>
    </div>
  );
}

export default ConfirmDialog;
````

**Qué hace y por qué:**

El diálogo de "¿Seguro?" por el que pasa **toda** acción destructiva (especificación 10).

- `useRef(null)` crea una "referencia" a un elemento de la pantalla; con `ref={cancelRef}` queda
  apuntando al botón "Cancelar".
- El efecto corre cuando el diálogo se abre: pone el foco en "Cancelar" (si alguien aprieta
  Enter sin mirar, no borra nada) y escucha la tecla Escape para cerrarlo, salvo que se esté
  borrando (`!loading`). La limpieza saca el escuchador: si no, quedaría uno colgado por cada

- `if (!open) return null` va **después** del `useEffect`: los hooks se llaman siempre, nunca
  después de un `return` (17-PLAN-FRONT, sección 8.3).
- `fixed inset-0` cubre toda la pantalla con un fondo negro al 40 % (`bg-black/40`); `px-4` deja
  margen a los costados para que entre a 360 px.
- `role="alertdialog"`, `aria-modal`, `aria-labelledby` y `aria-describedby` hacen que el lector
  de pantalla lo anuncie como diálogo y lea el título y el mensaje.
- Si el borrado falla, `error` se muestra **adentro** del diálogo, con un `Alert`.
- `flex-col-reverse sm:flex-row`: en el celular los botones van uno abajo del otro con

````jsx
// Generic table with loading, empty and error states. Below `lg` each row
// becomes a card with label/value pairs (spec 12.2).
// columns: [{ key, header, render(row), align: 'left'|'right', isAction }]
function DataTable({
  columns,
  rows,
  rowKey = (row) => row.id,
  loading = false,
  error = null,
  onRetry,
  empty,
  caption,
}) {
  if (error) {
    return (
      <div className="p-6 flex flex-col items-start gap-3">
        <Alert tone="error">{error.message}</Alert>
        {onRetry && (
          <Button variant="secondary" onClick={onRetry} className="min-h-11">
            Reintentar
          </Button>
        )}
      </div>
    );
  }

  if (!loading && rows.length === 0) {
    return empty;
  }

  const rowProps = { columns, rows, rowKey, loading };

  return (
    <div aria-busy={loading || undefined}>
      <div className="hidden lg:block overflow-x-auto">
        <table className="w-full text-left text-sm">
          {caption && <caption className="sr-only">{caption}</caption>}
          <thead className="bg-med-primary-50/70 text-[11px] uppercase tracking-wider text-med-text-sub border-b border-med-border">
            <tr>
              {columns.map((column) => (
                <th
                  key={column.key}
                  scope="col"
                  className={`px-6 py-3.5 ${alignClass(column)}`}
                >
                  {column.header}
                </th>
              ))}
            </tr>
          </thead>
          <tbody className="divide-y divide-med-border-subtle">
            <TableRows {...rowProps} />
          </tbody>
        </table>
      </div>

      <ul className="lg:hidden divide-y divide-med-border-subtle">

      </ul>
    </div>
  );
}
````

**Qué hace y por qué:**

La tabla genérica de todos los listados (especificación 10 y 12.2). Recibe las columnas como
datos y dibuja tres estados: cargando, vacío y error.

- **`columns`** es una lista de objetos: `{ key, header, render(row), align, isAction }`.
  `render` es una función que recibe una fila y devuelve qué dibujar en esa celda. Así la tabla
  no sabe nada de médicos ni de especialidades.
- **Error:** el mensaje y, si se pasó `onRetry`, el botón "Reintentar" (variante `secondary`).
- **Vacío:** si no está cargando y no hay filas, devuelve lo que llegó en `empty` (un
  `EmptyState` que arma cada página).
- **Cargando:** tres filas "esqueleto" que laten. `SKELETON_KEYS` son claves fijas para esas
  filas, porque la `key` nunca es la posición (17-PLAN-FRONT, sección 8.2).
- **Dos dibujos de lo mismo:** `hidden lg:block` muestra la `<table>` solo desde 1024 px, y
  `lg:hidden` muestra la lista de tarjetas solo por debajo (especificación 12.2: la tabla
  completa recién desde `lg:`). En la tarjeta, cada columna es un
  par etiqueta/valor (`<dt>`/`<dd>`) y la columna de acciones (`isAction`) va abajo a la
  derecha.
- `rowKey = (row) => row.id`: la `key` de cada fila es su `id`, salvo que se pase otra función.
- `<caption className="sr-only">` le da nombre a la tabla para el lector de pantalla y
  `scope="col"` marca que cada `<th>` es el título de su columna.
- `TableRows` y `CardRows` son componentes internos del archivo, para que `DataTable` quede corto.

### Qué problema resuelve

`SpecialtiesPage.jsx` del boilerplate es una página dibujada con una lista fija de cuatro
especialidades escrita en el código, cada una con su ícono SVG copiado. El buscador filtra esa

obligatorio." / "Eliminar si es obligatorio." Por eso esta tarea hace listado, alta y baja, y
la fila no tiene lápiz. Menos código para escribir y para probar.

### Por qué así

- **La forma de todo CRUD del proyecto.** La página compone; `SpecialtiesTable` dibuja;
  `useSpecialties` carga; `specialtiesService` habla con la API (17-PLAN-FRONT, sección 8.6). La
  tarea 4 copia exactamente esta forma.
- **Una tabla, no un listado propio.** `SpecialtiesTable` solo define las columnas y le pasa
  todo a `DataTable`, que ya trae los estados de carga, vacío y error, y las tarjetas en el
  celular (especificación 12.2).
- **El buscador es el `SearchInput` compartido**, así se cumplen las reglas de la 7.4 sin
  repetirlas: 3 letras mínimo, 400 ms de espera, sin `name` con el campo vacío y vuelta a la
  página 1 en cada búsqueda.
- **El formulario solo da de alta.** `SpecialtyForm` arranca vacío y la página llama a `POST`.
  No hay que cargar nada antes de dibujarlo, así que no hay spinner ni `reset()`.
- **Los errores del backend van donde corresponde** (especificación 6.4, 11.2 y P7):
  `SPECIALTY_DUPLICATED` debajo del campo Nombre; un `400` con `details` va a su campo (`applyFieldErrors`); cualquier otro, a un aviso
  arriba del formulario.

  listado y el listado muestra "Se creó la especialidad...".
- **Borrar pasa por `ConfirmDialog`**, y si el backend lo rechaza, el error queda adentro del
  diálogo. Si borrás la única fila de una página que no es la primera, vuelve a la anterior
  (especificación P3, casos borde; P6 dice "los mismos cuatro estados de P3").
- **Se quita la columna "Estado"** (especificación P6, decisión D38): una especialidad inactiva
  es una dada de baja, y esas no se listan. **Se quita el combo "Estado inicial"** del mockup de
  P7 por lo mismo.
- **Contador de caracteres en la descripción**: el mockup sugiere un texto largo, pero el máximo
  real es 100 (especificación P7).

````js
import { useCallback, useEffect, useState } from 'react';
import { getSpecialties } from '../services/specialtiesService';

const EMPTY_PAGE = { data: [], total: 0 };

// Paged list. Reloads when the params change; a stale response is ignored
// (spec 3.5). `reload` asks again with the same params.
function useSpecialties({ pageIndex, pageSize, name }) {
  const [page, setPage] = useState(EMPTY_PAGE);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);
  const [reloadKey, setReloadKey] = useState(0);

  useEffect(() => {
    let ignore = false;

    setLoading(true);
    setError(null);

    getSpecialties({ pageIndex, pageSize, name })
      .then((result) => {
        if (!ignore) {
          setPage({ data: result.data, total: result.total });
        }
      })
      .catch((apiError) => {
        if (!ignore) {
          setError(apiError);
        }
      })
      .finally(() => {
        if (!ignore) {
          setLoading(false);
        }
      });

    return () => {
      ignore = true;
    };
  }, [pageIndex, pageSize, name, reloadKey]);

  const reload = useCallback(() => setReloadKey((key) => key + 1), []);

  return {
    specialties: page.data,
    total: page.total,
    loading,
    error,
    reload,
  };
}

export default useSpecialties;
````

tarea 1 (17-PLAN-FRONT, sección 8.4): bandera `ignore`, limpieza, y `reload` con `reloadKey`.

  muestra `removal.error`. Si sale bien, muestra el aviso, cierra el diálogo y vuelve a cargar:

  `reload()`.

  dependencias de su efecto.
- **`empty`**: dos estados vacíos distintos (especificación P3/P6): con búsqueda, "No hay
  especialidades que coincidan con la búsqueda"; sin búsqueda, "Todavía no hay especialidades
  cargadas" con el botón de alta.

- `Card padded={false}`: la tabla ocupa todo el ancho de la tarjeta.

### Qué problema resuelve

`DoctorsPage.jsx` del boilerplate muestra cuatro médicos escritos en el código, con un emoji de
avatar y un "ID: MED-4920" inventado. El estado dice "Active" u "On Leave", que no existe en el

- **La misma forma que especialidades** (tarea 3): service, tabla, formulario y dos páginas. Lo que cambia es lo propio de un médico: el combo de especialidades, la matrícula
  opcional y el estado de agenda.

- **El combo de especialidades** usa `useSpecialtyOptions` (`pageSize` 100, especificación 7.5).
  Si no hay especialidades, el combo y el botón de guardar quedan deshabilitados, con el aviso
  "Primero tenés que crear una especialidad." y un enlace al alta (especificación P4).
- **El formulario se dibuja enseguida**, aunque las especialidades todavía estén llegando:

````jsx
    specialties.options.length === 0;

  // An empty license is sent as null (the column is nullable).
  const submit = (values) =>
    onSubmit(

      { setError, setValue }

      onSubmit={handleSubmit(submit)}
      noValidate
      className="flex flex-col gap-5"

        label="Nombre completo del doctor"
        required
        error={errors.name?.message}
      >
        <Input
          type="text"
          placeholder="Ej.: Dr. Juan Pérez"
          maxLength={100}
          {...register('name', {
            setValueAs: trimValue,
            required: NAME_MESSAGE,
            validate: (value) =>
              (value.length >= 3 && value.length <= 100) || NAME_MESSAGE,
          })}
        />
      </FormField>

      <FormField
        id="doctor-specialty"
        label="Especialidad"
        required
        hint={specialtyHint(specialties)}
        error={errors.specialtyId?.message}
      >
        <Select
          disabled={noSpecialties}
          {...register('specialtyId', { required: SPECIALTY_MESSAGE })}
        >
          <option value="">Seleccioná una especialidad</option>
          {specialties.options.map((specialty) => (
            <option key={specialty.id} value={specialty.id}>
              {specialty.name}
            </option>
          ))}
        </Select>
      </FormField>

      <FormField
        id="doctor-license"
        label="Número de licencia médica"
        error={errors.licenseNumber?.message}
      >
        <Input
          type="text"
          placeholder="Ej.: MP-12345"
          maxLength={LICENSE_MAX}
          {...register('licenseNumber', {
            setValueAs: trimValue,
            maxLength: { value: LICENSE_MAX, message: LICENSE_MESSAGE },
          })}
        />
      </FormField>

      <div className="flex flex-col-reverse lg:flex-row lg:justify-end gap-2">
        <Button
          variant="secondary"
          onClick={onCancel}
          disabled={isSubmitting}
          className="min-h-11"
        >
          Cancelar
        </Button>
        <Button
          type="submit"
          loading={isSubmitting}
          disabled={noSpecialties}
          className="min-h-11"
        >
          Crear médico
        </Button>
      </div>
    </form>
  );
}
````

**Qué hace y por qué:**

El formulario de P4. Sigue la forma de `SpecialtyForm` (tarea 3), con tres diferencias:

- **El combo de especialidades.** `specialties` es lo que devuelve `useSpecialtyOptions`:
  `{ options, loading, error }`. La primera opción tiene `value=""` y dice "Seleccioná una
  especialidad": como está vacía, la regla `required` falla si no se eligió otra. Las demás se
  arman con `map`, con `key={specialty.id}`.
- **`specialtyHint`** decide el texto de ayuda debajo del combo: "Cargando especialidades...",
  "No se pudieron cargar las especialidades", o el aviso con el `<Link>` a "Crear especialidad"
  cuando no hay ninguna. `<>...</>` es un *fragmento*: agrupa el texto y el enlace sin agregar
  una etiqueta. Si todo está bien devuelve `undefined` y no se muestra ayuda.
- **`noSpecialties`** es `true` si las especialidades están cargando, fallaron o no hay. En ese
  caso el combo y el botón de guardar quedan deshabilitados.
- La matrícula es opcional: solo tiene `maxLength` con mensaje (la forma de React Hook Form
  para el largo máximo) y el atributo `maxLength={LICENSE_MAX}` que no deja escribir más de 50.
- **`submit`** convierte la matrícula vacía en `null` (`values.licenseNumber || null`: si es
  `''`, usa `null`) y le pasa a la página `{ setError, setValue }`: `setValue` hace falta para
  vaciar el combo cuando la especialidad ya no existe.

````markdown
| P10 · Reservar turno        | `/`                                                              | `GET /api/specialties` · `GET /api/doctors?specialtyId` · `GET /api/doctors/{id}/slots?from&to` · `POST /api/appointments`      |
| P11 · Mis turnos            | `/appointments`                                                  | `GET /api/appointments/patient?dni` · `DELETE /api/appointments/{id}`                                                           |

Todos los endpoints, salvo los dos de login, requieren el token de la sesión; la app lo agrega
sola en el encabezado `Authorization`. Los errores del backend se muestran con el mensaje que
devuelve la API.

## Estructura

El código está organizado por funcionalidad (Screaming Architecture), en `src/modules`:

| Carpeta          | Contenido                                                 |
| ---------------- | --------------------------------------------------------- |
| `auth`           | Sesión, login de administrador y protección de rutas      |
| `dashboard`      | Plantilla de administración y tablero (P2)                |
| `specialties`    | Listado y formulario de especialidades (P6, P7)           |
| `doctors`        | Listado y formulario de médicos (P3, P4)                  |
| `availabilities` | Disponibilidad horaria por médico y mes (P5)              |
| `appointments`   | Búsqueda de turnos y cambio de estado (P8)                |
| `patients`       | Login, reserva y "Mis turnos" del paciente (P9, P10, P11) |
| `shared`         | Cliente HTTP, componentes, hooks y utilidades compartidas |

Dentro de cada funcionalidad, las capas dependen solo hacia abajo:
`pages → components → hooks → services → shared/api/axiosInstance`.

Reglas del proyecto:

- Ninguna funcionalidad importa de otra (salvo `auth`); lo que se comparte va a `shared/`.
- Solo los `services` usan Axios; los componentes nunca llaman a la API directamente.
- Los componentes compartidos siguen Atomic Design: `atoms`, `molecules`, `organisms` y `templates`.
- Los errores del backend llegan como `ApiError` (`status`, `errorCode`, `message`, `details`) y se
  muestran con el mensaje que devuelve la API.
````
